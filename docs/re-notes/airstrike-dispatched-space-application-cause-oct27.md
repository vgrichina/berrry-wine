## Exact binary path

Addresses below are original SDL preferred VAs. The retained runner loaded SDL at `0x536000`; runtime VA = original VA − `0x10000000` + `0x536000`. The EXE remains at its preferred `0x400000` base. Full hashes, byte excerpts and source line ranges are in [static-evidence.json](airstrike-dispatched-space-application-cause-oct27/static-evidence.json).

1. SDL registers its common Win32 procedure `0x10022480` (runtime `0x558480`): the WNDCLASS construction stores that pointer before RegisterClassA at `0x10022f03`. The external-window setup also installs that same procedure with SetWindowLongA at `0x1001442e`. The common procedure delegates unhandled messages through pointer `0x10039f0c`. DirectX setup assigns this pointer `0x100139a0` and the video pump callback `0x10013eb0` at `0x10014a2d..0x10014a55`.
2. The saved final main EIP `0x549d7f` is exactly `0x10013d7f` in the DirectX pump `0x10013c70`, immediately after WaitForMultipleObjects. This identifies the pump executing at the snapshot. It does **not** record the actual HWND procedure lookup, callback entry/return, backend-pointer value or earlier path through that pump.
3. The DirectX backend handler's byte-index/jump table maps **WM_KEYDOWN, WM_KEYUP, WM_SYSKEYDOWN and WM_SYSKEYUP** (`0x100/101/104/105`) to `0x10013a51`: pop registers, zero EAX, return. These messages do not call SDL's keyboard-event producer on this backend. All four table entries and the exact return bytes were checked directly in the pinned DLL. Dispatching Space therefore cannot by itself prove an SDL_KEYDOWN was created.
4. The DirectX pump first drains Win32 messages (`0x10013c85..0x10013cbf`), waits, then reads device data through vtable offset `0x28` at `0x10013dae`. A successful read, nonzero event count and enabled processing lead to the device callback at `0x10013e24`. Keyboard descriptor initialization selects `0x10013420`; that routine walks 16-byte device records, translates scan codes at `0x10014320`, and calls the private keyboard producer `0x1001a230`. The producer updates key state, checks event enable/filter gates and calls SDL_PushEvent (`0x10018970`) at `0x1001a436`.
5. SDL_PollEvent (`0x10018900`) pumps events and then calls SDL_PeepEvents (`0x10018670`) for one event, action2, mask `0xffffffff`. Its internal queue head/tail are `0x10035760/764`, records start at `0x10035768` with 20-byte stride. The caller needs a positive poll result and event type2, not merely an empty host FIFO.

## Application exit from the startup screen

The release source's `main` draws the startup message in `message_mode`, which draws one frame and calls `wait_for_key`. That loop returns on **any SDL_KEYDOWN**, ignores SDL_KEYUP, exits on SDL_QUIT and delays when no event is available. No Space-specific startup filter appears.

The actual EXE independently corroborates this: `0x413a39` loads the startup text at `0x42d3b8`, calls the message routine through `0x4110d2 → 0x412bf0`, and that routine calls `0x412750` at `0x412ca0`. The wait loop calls `0x41137f → 0x4292da → SDL_PollEvent` at `0x41277b`, tests result≥1, compares event type with2 at `0x412791`, and returns keysym from `[ebp-0x10]` at `0x4127b6`. Only afterward does main set up objects/players and print “Entering main loop.” See [the aligned wait-loop disassembly](airstrike-dispatched-space-application-cause-oct27/wait-loop.objdump.txt). The source archive is corroboration, not proof of a reproducible source-to-EXE build.
