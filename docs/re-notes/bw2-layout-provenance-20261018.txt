Current writer map (offsets are relative, not allocated memory bases)
The device's DxObject.misc1 selects its program. Program+8 is declaration,
+12 is FVF, +1740 is the active recording block. These are one layout selection.

1. src/09ad-handlers-d3d9.wat:47, d3d9_program_alloc zeroes the entire new
   program. CreateDevice installs it. Initial declaration/FVF/VS/PS are zero.
2. src/09ae-d3d9-resources.wat:589, d3d9_declaration_bind is the direct writer.
   Nonzero objects must have declaration magic and the same device owner;
   rejection returns INVALIDCALL without changing the pair. A valid live bind
   retains the new declaration before releasing the old one, writes declaration
   and clears FVF. A valid live NULL bind explicitly produces (0,0).
   While recording, it writes the block instead; live selection is untouched.
3. src/09ad-handlers-d3d9.wat:2061, SetFVF(0) is a successful no-op on a valid
   device, including recording (already fixed by 7e6948e75). Nonzero SetFVF
   records (0,FVF), or unbinds the live declaration then stores nonzero FVF.
   Its intermediate (0,0) has no host call/yield between the two writes.
4. src/09ae-d3d9-resources.wat:1334, block layout consists of mask+18936,
   declaration+18940, FVF+18944. The block owns its retained declaration.
   Begin/End recording alone does not apply it. CreateStateBlock types ALL(1)
   and VERTEXSTATE(3), but not PIXELSTATE(2), select the layout mask and capture
   the current pair. Capture also replaces the selected pair from live state.
   Transfer at1469 rejects Capture/Apply while this same device is recording.
   Apply at1634 uses the block's device owner, calls declaration_bind, then
   restores its recorded FVF. A masked (0,0) block therefore produces live
   (0,0) legitimately. An unselected layout mask cannot do so.
5. src/09al-d3d-reset.wat:18, Reset prepares a new zeroed program; the old
   program remains authoritative while backend completion is pending. Failed
   completion disposes the plan without installing the new pair. Successful
   completion installs the new program and releases old shader/declaration
   bindings; it preserves creation identity and resource registries, not layout.
   Recording and wrong creation-thread resets are rejected before installation.
6. Shared D3D8 adapters also call the same helper: SetVertexShader(handle) in
   src/09ac-handlers-d3d8.wat:635 binds its handle declaration; deleting a
   currently bound handle at1658 unbinds it. No evidence places these adapters
   on B&W2's D3D9 route. Shader binding alone does not install a vertex layout.

Host delivery boundary
src/09ad-handlers-d3d9.wat:136 constructs a reusable 64-byte descriptor inside
program+1744; descriptor+4 points to the program rather than copying layout.
lib/guest-rpc.js:423 routes D3D9 opcode0x30001 through brokerCall, whose
waitForResponse blocks the originating Worker with Atomics.wait. On the host,
lib/d3d9-host.js:1034 reads the live program pair and rejects (0,0) BEFORE
packing a draw. _issue at537 receives the packed payload; actual renderer queue
delay occurs after this check. Therefore later renderer queue consumption alone
does not explain the observed FVF0 rejection. This does not prove exclusion of
another guest thread mutating the same device before the broker reads it;
device/thread identity and issue-versus-host-read values still need correlation.

Producer hypothesis and evidence boundary
The strongest concrete historical lead is explicit guest NULL binding:
black-white-2.md's drive34 section recorded 48,043 NULL calls through engine
thunk0x009333f0; caller0x00a9cad0 loaded object+0x188. That older investigation
subsequently proved declaration-format rejection, since repaired. It is not
evidence that the later October9 descriptors used that caller or failed creation.
Hypothesis to discriminate: a live NULL bind (or Apply of a captured NULL
selection) occurs after the last valid layout and before the indexed draw,
with a nonzero VS still selected. Reset/init requires an intervening VS bind
to explain that descriptor. No source evidence chooses among these producers.
The old drive34 stateblock exclusion relied on a recording guard that no longer
applies to SetFVF: current SetFVF records correctly. Do not reuse that exclusion.

Smallest next observation, only after a separate runtime grant
Use existing filtered --trace-api (args/returns) for CreateVertexDeclaration,
SetVertexDeclaration, SetFVF, BeginStateBlock, EndStateBlock, CreateStateBlock,
StateBlock Capture/Apply, Reset, SetVertexShader and the indexed draw; use the
full IDirect3D method names. Existing --trace-host=gpu_gl_call logs import
arguments/return, but does not decode the pointed program or recording block.
Existing trace-api-mem can inspect a known pointer argument, not chase the
device's program dynamically. These flags alone cannot establish the pair.

If raw artifacts remain unavailable, a bounded trace needs a runtime-wrapper
observer at these existing trace boundaries, not a production renderer fallback.
For each selected API retain sequence, device, current/creation thread, args,
return, old/new program pointer, live pair, recording block and its mask/pair;
for a draw retain descriptor words and pair at issue and host read. Reset must
resolve program anew on return. Capture/Apply must derive device from the block.
Bound retention to the first rejected draw plus a small preceding ring; preserve
receiver, arguments, return values and exceptions, and restore any wrapper.
No observer was added now because its browser/Worker placement and source/module
identity cannot be validated without a grant; generic flags are not falsely
represented as sufficient producer instrumentation.
