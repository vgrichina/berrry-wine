## Read-only investigation

`spawnVfsChild` currently writes a file-only mutable snapshot and passes the
parent's actual cwd to the child. Provider-backed source files are correctly
omitted. No readonly directory tree or per-drive metadata accompanies that
snapshot, and the child correctly refuses an absent `d:\` cwd. Adding a bare
directory would conceal the lost media context.

The actual disc mount has label `THESIMS_COMPLETE`, serial `2782189353`,
drive type 5 and volume size 335261 sectors. Its provider is a ChunkCache
over the real CUE data-track provider. The provider cannot be reconstructed
by copying enumerable object properties; the underlying range reader is a
closure. Reopening original paths alone would also miss entry replacement
or adoption in the live parent filesystem.

A candidate transport will capture the actual readonly directories, provider
entries and per-drive metadata separately from mutable state. It reopens pinned
sources with the existing real mount plan and checks the resulting layout,
without downgrading synchronous providers to asynchronous RPC. The parent's
actual source ownership must fail if replaced or made writable. Profile inputs
use the mount plan's ordinary pre-execution materialization while retaining
borrowed provenance. Path validation, readonly writes and
the existing completion guard remain strict. No original launch is qualified
until the generated native parent/child inherits genuine D cwd, reads its
profile and verifies real merged C-file and registry writes.
