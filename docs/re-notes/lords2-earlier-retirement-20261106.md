## Demonstrated mismatch and repair

A generated NE uses real KERNEL.GlobalAlloc, USER.DialogBoxIndirect, GetDlgItem, SetWindowLong(-4), SendMessage and EndDialog. Its native Button child is subclassed with a generated far procedure. On both diagnostic modules before repair, EndDialog returned 42 and retired both windows, but root and child each received **zero actual WM_DESTROY and WM_NCDESTROY callbacks**. The observer distinguished attempted native delivery from guest entry: `win16_dlg_pump -> wnd_destroy_children -> wnd_destroy_tree -> wnd_send_message_inner` attempted an incomplete far WM_DESTROY before row removal; the root was removed directly. Native Wasm call stacks, live rows, owner/current task and full handles/generations are retained in `modal-baseline-standard/` and `modal-baseline-compat/`. This establishes a generated modal teardown defect, independently of the original installer.

Microsoft's [EndDialog contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enddialog) defers destruction until the dialog procedure returns. [WM_NCDESTROY](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-ncdestroy) follows WM_DESTROY and allows final window-data cleanup. Queuing a far callback and purging its HWND before entry does not satisfy delivery.

The repair reuses the existing Win16 far destruction walk before native modal removal. A 28-byte invocation-owned walk frame stores its cleanup mode. A separate 24-byte invocation-owned completion frame retains owner and screen bounds above the original modal result/far-return record. A new FFE4 continuation resumes modal restoration only after the walk finishes. No shared owner/result scratch or guest-map cleanup is introduced. Ordinary DestroyWindow retains its existing guard and cleanup policy; modal cleanup retains its existing owner/focus policy.

The first repair exposed an existing focus regression test: ordinary DestroyWindow's main-window fallback preselected an unrelated surviving window. Keeping modal cleanup separate fixed that failure. All focus target/result/stack assertions remain unchanged; the surviving-focus test now also expects the four newly delivered destruction callbacks while asserting no focus notifications.
