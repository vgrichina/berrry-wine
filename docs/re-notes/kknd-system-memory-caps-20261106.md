# DirectDraw system-memory blits and KKnD capability admission — 2026-11-06

The public COM matrix established software system-memory Blt support on both shipped modules, exposed packed-24-bit scalar corruption, and found incorrect success for `GetCaps(NULL, NULL)`. Both defects are repaired. HEL now reports the demonstrated support; HAL makes no new hardware claim. The one original registered KKnD session passed DirectDraw setup, reached the main menu and visible Evolved gameplay, and showed unit selection brackets. The original KKnD setup rejection is inferred from retained modal stack buffers and original disassembly, not a captured GetCaps HRESULT or branch trace. HAL and HEL both contained `dwCaps=0x24041`, omitting `DDCAPS_CANBLTSYSMEM=0x80000000`. Omitting this optional bit is not itself an implementation defect. See [the prior original session](kknd-origin-worker-gameplay-20261106.md) and its retained `capability-boundary.json`.

Microsoft documents [GetCaps](https://learn.microsoft.com/en-us/windows/win32/api/ddraw/nf-ddraw-idirectdraw7-getcaps) as separate hardware-driver and HEL outputs, and requires failure when both outputs are NULL. [DDCAPS](https://learn.microsoft.com/en-us/windows/win32/api/ddraw/ns-ddraw-ddcaps_dx5) distinguishes system-to-video, video-to-system and system-to-system transfers. A measured CPU implementation can establish software support; it cannot establish hardware acceleration.

The [public COM fixture](../../test/test-directdraw-system-memory-blits.js) generates guest x86 indirect-vtable calls with independently specified slots/argument counts and exact stdcall stack checks. It creates surfaces through DirectDraw7 and includes a legacy DirectDraw1/Surface1 indexed caller-to-video case. Both shipped modules were instantiated directly, with exact module bytes/hash recorded. No private handler is invoked and no synthetic surface metadata is installed. Factory dispatch uses the existing catalog-thunk harness; normal PE loading and COM-thunk initialization precede the calls.

The matrix covers allocated system-memory storage, caller-owned padded storage, video-labelled offscreen storage, full copies, subrectangles, destination-bound trimming, nearest-neighbor stretch, source keys, disjoint explicit clip lists and color fill. Formats are indexed8, RGB565, RGB555, ARGB1555, ARGB4444, BGR24, XRGB32 and ARGB32, with descriptor masks checked. Expected pixels come from an immutable source snapshot and coordinate arithmetic, independently of WAT traversal. Full destination rows, padding, caller allocation guards and source immutability are checked. References, caller storage after Release, descriptor guards, malformed GetCaps output and both-NULL GetCaps are covered.

[Blt](https://learn.microsoft.com/en-us/windows/win32/api/ddraw/nf-ddraw-idirectdrawsurface7-blt) documents all four memory directions, null rectangles, stretch and color keys. Destination-bound trimming without an attached clipper is recorded as existing emulator behavior, not a native acceptance oracle. [BltFast](https://learn.microsoft.com/en-us/windows/win32/api/ddraw/nf-ddraw-idirectdrawsurface7-bltfast) is documented only for display-memory surfaces and must reject an attached clipper. System-memory BltFast success is recorded separately as an existing emulator extension, not capability evidence.

The rejecting controls cover exact `DDERR_UNSUPPORTED` for BltFast with an attached clipper, unchanged destination bytes on that failure, atomic rejection of a malformed second GetCaps buffer, and exact `DDERR_INVALIDPARAMS` for both NULL outputs. Formats are matched between source and destination: this matrix does not qualify cross-format conversion, negative pitch, 4bpp, arbitrary ROPs, alpha blending, or all invalid rectangle/flag combinations. Source inspection suggests broader format-admission and BltFast out-of-bounds behavior deserve separate qualification; neither is silently treated as proven support here.

Before repair, each shipped module produced 422 observations and 1,075 COM calls, with 21 identical failures: five BGR24 operations in each of four storage configurations (stretch, keyed stretch, explicit clipping, keyed clipping, fill), plus both-NULL GetCaps. Ordinary packed-24 copies already passed. Scalar paths incorrectly used DWORD loads/stores and four-byte pixel indexing for three-byte pixels, damaging neighboring pixels or padding. The repair uses exact three-byte loads/stores and the actual byte stride. Both-NULL GetCaps now fails before writing either output. The repaired pixel matrix passed on both modules before changing capabilities; see `baseline-*.log` and `repaired-*.log`.

Only HEL adds `DDCAPS_CANBLTSYSMEM`: HAL remains `0x00024041`, HEL is `0x80024041`. HEL's system-to-video, video-to-system and system-to-system directional caps at offsets 172/216/260 advertise ordinary `DDCAPS_BLT=0x40`; their additional color-key, effect and ROP fields remain clear. This deliberately conservative report follows the measured CPU path and does not assert GPU acceleration. It does not reinterpret the earlier optional omission as a defect.
