## Where host consumption stops proving progress

The production `h.check_input` implementation is byte-identical between retained runtime Git `1188e9bf57ef35bd3363fb88b7ca0da442ce696d` and this checkout. It calls `renderer.takeInput`, sets host `_lastInputEvent` and renderer `_activeInputEvent`, logs `[input]`, and returns a packed message. An empty poll clears those host fields. Therefore the observed console lines are emitted **before the guest receives or dispatches its MSG**.

The retained/current WAT message, dispatch and tracing fragments are identical. `PeekMessageA` can retain hardware input in `pending_input_packed`, route it to its owner, admit it through the guest's filters or move an excluded event into the posted queue. `GetMessageA` has its own delivery path. Neither host queue drainage nor a frozen-step ACK says the application subsequently called `DispatchMessageA` with that event. DispatchMessage's x86 path constructs a WndProc frame and redirects EIP; that is another boundary after its API entry. The production Worker broker captures forwarded API arguments inside the calling Worker because the page instance's registers are not authoritative. This observer follows that same rule; page-register sampling would be insufficient.

## Tested observer and next boundary

`observer.cjs` attaches synchronous wrappers to the existing Worker `host.log` API-entry hook and `host.log_block(eip,esp)` trace hook. It must be attached to the import object **before instantiation**, with an exports getter bound to that same instance and `translate: self.memUtils.g2w` from the existing production memory utility. The pure JS translator reads packed mappings without calling the WAT translator; a WAT translation miss can touch the sentinel or raise a guest exception, so it is deliberately never invoked by this observer. It remains inactive until explicit `start()` at a qualified frozen boundary. It validates the externally preflighted EXE SHA, preferred base and original instruction signatures. Records include Worker slot, live guest thread ID, stack arguments, EAX/ECX/ESI, current/requested scenes, hover ID, raw button record state and guest mouse fields. API-entry rows copy the actual DispatchMessageA MSG synchronously. Block rows distinguish WndProc, guest mouse update, evaluator, hit-test return, press callback, ID2 branch and scene request. They are observations, not replacements for game calls.

For a separately authorized original run, attach the helper in each relevant Worker's existing instantiation instrumentation; retain all original import forwarding. Before the same normal reviewed gesture, use the **existing diagnostic** `set_api_log(1)` and `set_trace_esp` controls on the owning instances. The smallest first-boundary configuration is callback range **`0x430e10..0x430f15`**, together with DispatchMessage API rows and `sample()` at existing pre/post ACK boundaries. This directly answers the currently missing callback ID/request question. To collect every supported upstream block in that same one-gesture window, the inclusive range is **`0x430e10..0x4e9723`**. That wider diagnostic range forwards many unrecorded blocks through the original broker and can substantially perturb timing; it is not qualified as a cheap gameplay configuration. Neither configuration was executed here. Do not infer timing or absence from an incomplete trace.

Keep the current initial ChooseType, exact specific hover, personal review/fresh recapture, native mapping, ownership, complete ACK/drain, first-failure terminal and native Start guards unchanged. Observer installation is not a substitute for those prerequisites. End recording at the existing terminal boundary; do not add settling input or a retry. Export each instance's `report()` while still frozen. Storage is capped at 1024 rows by default, with explicit drop/error reporting; trace arming and Worker coverage remain independently **unqualified** in reports. An absent callback row alone is not proof that it never ran. `detach()` restores only wrappers it still owns. No guest setter, guest invocation, forced scene, memory write, counter reset or input occurs inside the observer.
