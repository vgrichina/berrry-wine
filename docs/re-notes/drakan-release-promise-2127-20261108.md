# Drakan WorkerLink release Promise repair

Repaired the release wrapper published in `6fc4d59ca94ceec263b7855c5d3a483295223c4c`. Evidence is in `scratch/runs/20261108-drakan-release-promise-2127/`. This is synthetic qualification through the production Worker, WorkerLink and GuestThreadHost; no Chrome, game, original, input injection, remote resource or additional worker agent was used.

The actual GuestThreadHost reproduction reported `releasePromiseSettledBeforePhysical:true` for delayed success and delayed rejection. Rejection left `Controller.releaseError` null and produced `unhandledRejection: Error: delayed physical release rejection`. Both results are retained in `reproduce-before.log.gz`. The same reproduction after repair reports false, records the rejection in `releaseError`, and observes no unhandled rejection (`reproduce-after.log.gz`).

`WorkerLink.observeDrakanActor` now invokes the external callback once and caches its Promise for every duplicate invocation. Native Promise identity is preserved; other results are normalized with `Promise.resolve`. A synchronous throw becomes a cached rejected Promise, so it cannot replace the original setup error or bypass the existing Controller rejection handler. An immediate rejection handler also covers the independent setup timer before a Controller exists. The Controller still clears its shared action to down=false/UNKNOWN before release initiation. That state is not a receipt that physical input was released.

Controller release settlement follows the existing API: `await controller.releasePromise`, then inspect `controller.releaseError`. The Promise handles rejection and fulfills after recording it. Setup errors now expose the same interface as `error.releasePromise` and a live `error.releaseError` getter, even when construction failed and no Controller was retained. The original setup error remains the thrown failure. `onStop` remains an immediate notification; its initial error snapshot can precede asynchronous release failure, so callers must join the live release result. No Worker or retirement method awaits physical input I/O.

Dependency loading remains inside the original action deadline. Setup cannot create a new Controller after release initiation or WorkerLink retirement. The independent release cap remains at most 2000 ms; controller deadlines retain the original action start. Completion, owner, pin, freshness and enclosing-return requirements are unchanged. There is no down injection, second action, rearm or replay in the repair.
