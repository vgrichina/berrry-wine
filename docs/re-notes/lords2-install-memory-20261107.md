Task: NEW-GAME-LORDS2-DEMO-20261015. Evidence: `scratch/runs/20261107-lords2-install-memory/`. Follows [the PIT calibration repair](lords2-pit-calibration-20261107.md). Aranna released shared runtime/source/build at 01:45:13Z; its processes, ports, profiles and all four locks were independently checked before runtime work.

The preceding original's `first-remaining-blocker.json.gz` establishes more than the final dialog. Child selector 0047 is the runtime's original segment 1, base 00170000. Segment 0057:4024 initializes a 64,000-byte buffer size and calls 0047:1D13 with that size. The C-runtime allocator searches existing blocks, attempts growth, and finally attempts a new arena. The new-arena routine at 1FB8 computes `(request + 0x1019) & 0xF000` in 16 bits. For 64,000 this wraps to zero, representing a whole 64 KiB block. At 1FCF it tests BX bit 0x10; the unique captured context has low BX=00D4, CX=DX=0. The branch takes 2035, which returns carry set without calling GlobalAlloc. The allocator's failure handler ultimately selects message resource F10A, then USER.1 displays the retained insufficient-memory text. This is a guest policy decision made before the candidate allocation reaches the emulator's allocator.

BX comes from `MOV BX,CS:[0010]`. The retained original child recovered from a prior ordinary setup has SHA-256 `7dbf696d4f08464ca1e187686368fe89c5b71b3162c094f463d0e5ec4eaca567`, 528,080 bytes, at `scratch/runs/20261105-lords2-recovered-original-gameplay/generated-setup.exe`. Its original segment-1 relocation at offset 0010 is address type 5 (OFFSET), import ordinal, module KERNEL, ordinal 178. This is `__WINFLAGS`, an absolute export, rather than a callable entry point. The retained malloc code matches this interpretation: bit 0 controls the protected-mode API path and bit 0x10 the standard-mode allocation restriction. The runtime value 00D4 is a thunk offset substituted by our ordinary import resolution. It is neither an observed allocation failure nor evidence that available physical memory is too small.

[Wine's KERNEL export specification](https://github.com/wine-mirror/wine/blob/master/dlls/krnl386.exe16/krnl386.exe16.spec) declares ordinal 178 as an equate. Its [KERNEL initialization](https://github.com/wine-mirror/wine/blob/master/dlls/krnl386.exe16/kernel.c) sets that entry point from GetWinFlags16. Our current absolute-import resolver handles __AHSHIFT and __AHINCR but not __WINFLAGS; its OFFSET relocation therefore writes an allocated thunk offset. The repair adds ordinal 178 to that existing constant-resolution path, using a shared helper for the existing GetWinFlags expression. It changes no machine-result value, timer/calibration output, guest configuration, media or installer check. The guest continues to execute its own policy with the correctly represented export.
