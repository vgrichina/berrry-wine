Result
The next useful experiment is the native DirectDraw7 cube surface creation /
face retrieval contract, before shader or pixel work. The legacy path inspected
below loses the second capability DWORD at both creation and retrieval. A cube
implementation needs face identity and independent backing before its sampler
can be qualified. This is a concrete source mismatch, not a measured HRESULT
or a recommendation to clear the advertised bit without caller tests.

Primary contract (retrieved 2026-10-18)
Microsoft DDSCAPS2 documents CUBEMAP plus face flags as creation requests;
ALLFACES requests six faces. MIPMAPSUBLEVEL distinguishes attached mip levels
from top-level faces when GetAttachedSurface selects among them.
https://learn.microsoft.com/en-us/windows/win32/api/ddraw/ns-ddraw-ddscaps2
Microsoft GetAttachedSurface7 takes DDSCAPS2, returns the matching interface
with an added reference, and fails ambiguous matches.
https://learn.microsoft.com/en-us/windows/win32/api/ddraw/nf-ddraw-idirectdrawsurface7-getattachedsurface
These are API contracts, not the modern DDS file-storage convention. In
particular do not import the DirectX8 requirement for all six DDS file faces
into a legacy partial-face CreateSurface rejection rule.

Bit identity is the previously corrected legacy header mapping: texture cap
CUBEMAP=0x0800, not 0x0400 (PROJECTED). The retained correction cites Wine's
include/d3dcaps.h; Microsoft D3DPRIMCAPS search snippets mention CUBEMAP, but
the presently retrieved Learn page and its raw MicrosoftDocs source do not.
Do not treat that search snippet as an independently recovered DX7 SDK header.
This audit depends on the DDSCAPS2 API contract, not a newly invented bit map.

Implementation evidence (baseline symbols, line numbers are navigational)
src/09a8-handlers-directx.wat:
- fill_primcaps:3565 writes 0xFFDF at primitive-cap offset32; cube bit remains
  advertised. SQUAREONLY is already clear and is outside this work.
- dx_get_ddraw7_vtbl:1975 extends the earlier interface table; this only adds
  tail slots. It is not a distinct CreateSurface implementation.
- handle_IDirectDraw_CreateSurface:2624 reads dwCaps at DDSURFACEDESC +104.
  It does not load the DDSURFACEDESC2 dwCaps2 at +108. Its branches allocate
  ordinary surface, mip chain, or flip chain. At2813 it creates DDSURF2;
  at2822 it zeros16 bytes of surface metadata and at2832 stores only dwCaps.
  Merely allocating six textures elsewhere cannot fix this entry point.
- handle_IDirectDrawSurface_GetAttachedSurface:6242 loads only the first
  DWORD from the requested caps pointer. Selection compares that value with
  stored first-DWORD caps, via implicit links or dx_surface_explicit_child.
  It therefore cannot distinguish +X from -X requests differing only in
  dwCaps2. The existing successful lookup does add a reference.
- handle_IDirectDrawSurface_GetCaps:6318 intentionally implements the
  one-DWORD Surface1/2/3 output. A cube patch must not make this legacy method
  blindly write16 bytes into old callers' four-byte buffers.
src/09ab-handlers-d3dim-core.wat:
- d3dim_texture_sample_rgb:4652 and d3dim_texture_sample_prepared:4800 accept
  U/V, not a three-component cube direction or face collection.
lib/d3dim-gpu.js:
- _texture constructs {width,height,key} at653 from one decoded pixel image.
- _draw sets U/V addressing and mip0 at783. This path does not publish faces
  to the modern backend. Modern D3D8/9 cube support alone is no legacy proof.
These observations are intentionally scoped to these paths, not a global
assertion that no cube-related code exists elsewhere in the repository.

Exact next executable fixture (new JS, coordinator runtime grant required)
1. Use real guest COM calls through DirectDrawCreateEx(IDirectDraw7), then
   its CreateSurface slot6, not a direct helper export or the VB wrapper.
   Record returned vtable/slot routing and ESP. Request a 4x4 uncompressed
   32-bit RGB surface with DDSURFACEDESC2 size124, DDSD_CAPS|HEIGHT|WIDTH|
   PIXELFORMAT, caps TEXTURE|COMPLEX|SYSTEMMEMORY, caps2 CUBEMAP|ALLFACES.
   No mipmaps, palettes, keying, alpha blend, or GPU are needed in this phase.
2. Query returned descriptor/caps through the actual returned surface ABI;
   retain poison sentinels around outputs. Walk faces through the documented
   face flags using GetAttachedSurface slot12, with the creation root handled
   separately if it is itself the requested face. Require six face identities
   and independent Lock/write/Unlock/readback colors; allocation success alone
   is not a pass. Record HRESULTs and reference/release effects explicitly.
3. Negative control: same first DWORD, two different face bits in dwCaps2
   must resolve distinct faces. This specifically catches the present request
   truncation. Also keep ordinary 2D + mip/flip attachment controls to protect
   existing callers; ambiguous face selection must not silently pick one.
4. First implementation slice: version-aware surface ABI / descriptor handling,
   preserved caps2 and explicit cube owner-face metadata, failure-atomic face
   allocation, correct face lookup with AddRef/Release. Keep legacy one-DWORD
   buffers untouched. No speculative caps removal or silent 2D success.
   Decide any error-policy details not supplied above against a versioned SDK
   or reference run rather than making fixture expectations from current code.
5. Only after API/storage pass: carry the third coordinate through legacy
   vertex/FVF/transform/raster paths and publish six faces to the GPU adapter.
   Add six axis-centre samples (+/-X,Y,Z), independent face mutations, and
   interior off-axis orientation samples on software, WebGL1, WebGL2 and both
   Worker routes. Six solid face colors test selection, not orientation/seams.
   Include actual route counters and zero unexpected fallbacks. Those future
   tests are required before claiming cube renderer qualification.
