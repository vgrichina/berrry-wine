## Return, timing and lifetime boundaries

The read-only exact-main WinExec handler passes its name marker to shell_execute and returns the callback's integer unchanged; its exact blob and slice are retained here.

CLI status is synchronous: missing/unresolvable/export-unavailable executable maps to 2, thrown synchronous transport/resource failure to 0, accepted fork to 33. Private transport PID 0x4004 stays in process_ctl and is never returned as the shell status. Guest completion is asynchronous and uses the existing merge/exit tracking. This is transport acceptance, not guest startup/PE validation or installation success. As before, the transport cannot synchronously report later OS fork error events, child PE-loader failures, ERROR_BAD_FORMAT or readiness. The repair does not implement WinExec's documented GetMessage-or-timeout startup wait. Full Windows search-path semantics and executable associations remain existing parser/resolver/transport behavior; CreateProcess's API contract is not asserted interchangeable with WinExec. Independent review must assess those limits before runtime use.
