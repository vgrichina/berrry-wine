## Exact instrumentation blocker and control

Existing features were inspected first in the hash-matched runner. `--trace-api-mem` dereferences stdcall arguments at entry and successfully captured the text/COM GUID bytes. `--trace-at-mem` supports one pointer dereference and fixed/register-relative reads. Multi-address `--trace-at` changes BATCH_SIZE to1, arms only the first WASM breakpoint, and samples other addresses at block boundaries; it cannot guarantee arbitrary interior-instruction/return captures. Fixed `--trace-at-dump` cannot by itself chase returned objects or read per-child native state without allocation. The chosen fallback wraps the **existing** `--trace-eip-range` block-entry import and API logger in a copied harness, retaining the ordinary batch budget.

[harness.patch](harness.patch), [observer.js](observer.js), [prepare.py](prepare.py) and [driver.py](driver.py) preserve the exact implementation. The observer only uses exported register/image-base getters, direct DataView reads, pure address translation, and host-side maps/output. It calls no guest allocator, text getter requiring a destination, SendMessage, setter, breakpoint, timer, scheduler or capability API. The historical module and retained runner were unchanged. Built-in tracing introduces host overhead and diagnostic dispatch paths; timing/performance equivalence is not claimed. The custom hook adds no guest values or scheduling settings beyond those existing trace flags.

The1600th and last event is ReadFile on `c:\art\art1.bar`, not XML. The preserved full log contains **1600 observer events, zero block records**. The remaining native HRESULT and table/lookup/dispatch-return instrumentation was consequently silent. This was not a guest stop, API denial or engine trap. The built-in API traces continued and supplied the limited evidence above.
